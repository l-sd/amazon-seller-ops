# 日常运营：先排销售阻断，再复盘经营

## 输入与范围

读取用户已有店铺、站点、时区、币种、履约方式（FBA/卖家自配送）及责任范围。缺少时先提出影响分析的问题。只有公开资料则只能研究页面与竞品；账户健康、真实订单、广告表现、库存数量均不可确认。

| 工作 | 资料从哪里来 | 形成什么 |
|---|---|---|
| 账户/商品销售状态 | Seller Central 的 Account Health、通知、Manage All Inventory、受限/不可售记录 | 有证据的异常、受影响 ASIN、期限、提交主管事项 |
| 订单与客服 | 获准使用的 Manage Orders、买家消息、退款/退货导出，尽量去除买家身份 | 超时/履约或产品问题分类；回复草稿，不自动发送 |
| 库存与入仓 | FBA 库存、不可售/预留/在途、入库状态、SKU 日销与供应链交期 | 断货风险、缺失 ETA、补货评审项 |
| 销售日报 | Reports → Business Reports → By Date 的销售与流量导出 | 订购销售额、件数、订单项、同日对比和待核查原因 |
| 广告 | 广告控制台 Campaign Manager 和对应 SP 报表 | 花费/预算异常提示；按归因窗口分开的搜索词复盘 |
| 页面与客户体验 | 自己的具体变体商品页、VOC/退货原因、公开评价和反馈 | 价格/可购买状态、信息错配、页面或产品改进项 |

入口为功能名参考，实际界面和权限按执行时官方帮助核对；不能把旧页面路径写成必然存在的按钮。

## 工作节奏

每天先看不可售、账户通知、履约/消息时限和断货紧急项，再产出销售摘要与明显的花费异常。日常“看广告”不等于每天改竞价。深入搜索词/位置、页面、库存和费用复盘可按业务量每周安排；有突发异常则提前处理。卖家社区的分工节奏只是参考，不强制周一到周五固定任务。[实务来源 C1/C2、官方 O1/O5，见 sources.md]

1. **销售变化**：先核对日期是否完整、币种/时区/导出范围是否一致；再查能否售卖、库存、报价和配送，随后比较流量、订购件数/会话。没有 SKU 明细就不能指出“某 SKU 导致下跌”。遇到缺日不当成零，不给因果断言。
2. **广告复盘**：先核对 SP 与归因窗口；按“相关性 → 样本和归因完整性 → 表现 → 利润目标/库存约束”判断。有花费无订单只是复核候选，不自动否定。迁词、预算和竞价提供草稿及影响，不执行。缺商品对应关系则不强行把广告活动归到 SKU。
3. **库存评审**：有同 SKU 的完整日销量才算 7/14/30 日均，记录缺货期间可能压低需求。`可售库存/日均销量` 只是当前可售覆盖天数；在途按每批 ETA 单列，不把所有在途当作今天可售。与生产、运输、清关、接收和安全缓冲比较；缺日销或交期就标“无法计算”，不套用固定库存件数线。
4. **客户体验**：区分商品评论、卖家反馈、VOC 和退货原因。围绕误购、兼容、损坏、说明不清整理证据；优先事实核查与产品/页面改进，不用退款交换评价。疑似安全故障交主管，不指导危险拆修。

## 日报与周报交付

简述已检查的范围，给同口径指标与对比；列“已观察异常/可能解释/还需查看的数据/建议动作/责任人待确认/复查节点”。账户健康等未提供资料写“未检查”，不是“正常”。已生成日报不代表已向主管发送。

数据处理调用 report-tools.md。周报在日报基础上按活动/商品资料可用性拆分，结合改动日志和库存；效果对比须说明促销、缺货、价格或季节等干扰因素。只有观察性前后变化时不写成某动作带来的确定提升。
